  1. RINGKASAN EKSEKUTIF
================================================================================

Blockchain di SIMARC adalah sistem pencatatan riwayat perubahan data (audit
trail) yang menggunakan prinsip cryptographic hash chaining untuk memastikan
integritas dan keabadian catatan (immutability).

BUKAN cryptocurrency -- tidak ada token, mining, konsensus terdesentralisasi,
atau smart contract. Blockchain SIMARC adalah private, permissioned blockchain
dengan otoritas tunggal (single authority) yang digunakan sebagai mekanisme
anti-tamper untuk data kearsipan.

  Tujuan utama:
  (a) Mendeteksi manipulasi data arsip (baik disengaja maupun tidak)
  (b) Menyediakan bukti kriptografis atas setiap perubahan data
  (c) Memberikan transparansi penuh atas riwayat akses dan modifikasi arsip
  (d) Memenuhi standar kepatuhan arsip (audit trail immutable)


================================================================================
  2. KONSEP DASAR BLOCKCHAIN
================================================================================

  2.1. Apa itu Blockchain?

  Blockchain adalah rantai blok yang saling terhubung secara kriptografis.
  Setiap blok berisi data transaksi dan hash dari blok sebelumnya, membentuk
  rantai yang tidak bisa diubah tanpa memutuskan tautan kriptografis.

  Dalam konteks SIMARC, "transaksi" adalah operasi CRUD (Create, Read, Update,
  Delete) pada data arsip.

  2.2. Mengapa Blockchain diperlukan untuk sistem kearsipan?

  (a) Keaslian arsip (authenticity) -- bukti bahwa data belum diubah sejak
      pencatatan
  (b) Integritas arsip (integrity) -- mendeteksi perubahan data ilegal
  (c) Keabadian (immutability) -- catatan tidak bisa dihapus atau diubah tanpa
      meninggalkan jejak
  (d) Transparansi -- seluruh riwayat perubahan dapat diaudit kapan saja
  (e) Akuntabilitas -- setiap perubahan tercatat dengan identitas pengguna dan
      timestamp

  5. ALGORITMA PEMBUATAN BLOK
================================================================================

  5.1. Flow Pembuatan Blok (RecordAudit)

  Langkah-langkah ketika sebuah transaksi dicatat:

  Step 1: Transaksi terjadi (arsip dibuat/diedit/dihapus/diimport)

  Step 2: Ambil blok terakhir dari database:
          SELECT * FROM blockchain_audits
          ORDER BY block_number DESC LIMIT 1

          Jika belum ada blok: blockNumber = 1, previousHash = ""
          Jika ada:
              blockNumber = lastBlock.BlockNumber + 1
              previousHash = lastBlock.CurrentHash

  Step 3: Siapkan data untuk di-hash:
          blockData = entityType + ":" + entityID + ":"
                     + action + ":" + details + ":"
                     + previousHash

  Step 4: Hitung SHA-256 hash:
          currentHash = SHA-256(blockData)

  Step 5: Simpan blok baru ke database:
          INSERT INTO blockchain_audits (
              uuid, previous_hash, current_hash, block_number,
              timestamp, user_id, action, entity_type,
              entity_id, details, ip_address, user_agent, is_valid
          ) VALUES (
              uuidBaru, previousHash, currentHash, blockNumber,
              timestampRFC3339, userID, action, entityType,
              entityID, detailsJSON, ipAddress, userAgent, true
          )

  5.2. Implementasi Kode (Go)

  func (s *BlockchainAuditService) RecordAudit(
      entityType, entityID, action string,
      data interface{}, userID string,
      ipAddress, userAgent string,
  ) error {
      dataBytes, _ := json.Marshal(data)
      details := string(dataBytes)

      var prev models.BlockchainAudit
      database.DB.Order("block_number DESC").First(&prev)

      blockNumber := uint64(1)
      if prev.BlockNumber > 0 {
          blockNumber = prev.BlockNumber + 1
      }

      timestamp := time.Now().Format(time.RFC3339)
      uuid := uuid.New().String()

      blockData := fmt.Sprintf("%s:%s:%s:%s:%s",
          entityType, entityID, action, details, prev.CurrentHash)
      currentHash := sha256sum(blockData)

      var uidPtr *string
      if userID != "" {
          uidPtr = &userID
      }

      audit := models.BlockchainAudit{
          UUID:         uuid,
          PreviousHash: prev.CurrentHash,
          CurrentHash:  currentHash,
          BlockNumber:  blockNumber,
          Timestamp:    timestamp,
          UserID:       uidPtr,
          Action:       action,
          EntityType:   entityType,
          EntityID:     entityID,
          Details:      details,
          IPAddress:    ipAddress,
          UserAgent:    userAgent,
          IsValid:      true,
      }
      return database.DB.Create(&audit).Error
  }

  5.3. Fungsi Hash SHA-256

  func sha256sum(s string) string {
      h := sha256.Sum256([]byte(s))
      return hex.EncodeToString(h[:])
  }


================================================================================
  6. ALGORITMA VERIFIKASI CHAIN
================================================================================

  6.1. Flow Verifikasi (VerifyChain)

  Step 1: Ambil SEMUA blok dari database, urut ASC berdasarkan
          block_number

  Step 2: Untuk setiap blok (i = 0 hingga n):

    2a) Hitung ulang hash yang SEHARUSNYA:
        expectedHash = SHA-256(
            entityType + ":" + entityID + ":"
            + action + ":" + details + ":"
            + prevRecalculatedHash
        )
        Note: prevRecalculatedHash adalah hash YANG DIHITUNG
        ULANG dari blok sebelumnya, BUKAN previous_hash yang
        tersimpan di database.

    2b) Bandingkan expectedHash dengan stored currentHash:
        - Jika cocok  -> blok VALID
        - Jika berbeda -> blok INVALID

    2c) Simpan expectedHash sebagai prevRecalculatedHash untuk
        iterasi berikutnya

  Step 3: Hasil verifikasi:
    {
        "total_blocks":          jumlah seluruh blok,
        "invalid_blocks":        jumlah blok tidak valid,
        "invalid_block_numbers": [daftar nomor blok],
        "is_valid":              true jika invalid_blocks == 0
    }

  6.2. Mengapa menggunakan prevRecalculatedHash, bukan previous_hash?

  Ini adalah aspek keamanan KRUSIAL.

  Jika seorang attacker berhasil mengubah nilai current_hash dan
  previous_hash di database, verifikasi yang hanya memeriksa
  previous_hash tidak akan mendeteksi perubahan.

  Dengan menghitung ulang hash dari awal (prevRecalculatedHash), kita
  membuat "trustless verification" -- integritas chain tidak bergantung
  pada data yang tersimpan di database, melainkan pada konsistensi
  matematis antara hash yang dihitung ulang.

  Visualisasi perbedaan:

  DATABASE TERSIMPAN:                    VERIFIKASI:
  +----------+                           +----------+
  | Blok #1  |                           | Blok #1  |
  | prev: "" |                           | (hitung hash dari data)
  | hash: A  |                           | hash = A valid
  +----+-----+                           +----------+
       | prev_references                        | prev_recalculated = A
       v                                        v
  +----------+                           +----------+
  | Blok #2  |                           | Blok #2  |
  | prev: A  |                           | (hitung hash dari data + A)
  | hash: B  |                           | hash = B valid
  +----+-----+                           +----------+
       | prev_references                        | prev_recalculated = B
       v                                        v
  +----------+                           +----------+
  | Blok #3  |                           | Blok #3  |
  | prev: B  |                           | (hitung hash dari data + B)
  | hash: C  |                           | hash = C valid
  +----------+                           +----------+

  Jika attacker mengubah data di Blok #1 dan menyesuaikan hash:

  DATABASE (MANIPULASI):                 VERIFIKASI (DARI AWAL):
  +----------+                           +----------+
  | Blok #1  |                           | Blok #1  |
  | prev: "" |                           | (hitung hash dari data ASLI)
  | hash: X  | (diubah)                  | hash = X != A -> INVALID!
  +----------+                           +----------+

  6.3. Implementasi Verifikasi (Go)

  func (s *BlockchainAuditService) VerifyChain() map[string]interface{} {
      var records []models.BlockchainAudit
      database.DB.Order("block_number ASC").Find(&records)

      invalidBlocks := 0
      invalidBlockNumbers := []uint64{}
      prevRecalculatedHash := ""

      for i := 0; i < len(records); i++ {
          expectedHash := sha256sum(fmt.Sprintf("%s:%s:%s:%s:%s",
              records[i].EntityType, records[i].EntityID,
              records[i].Action, records[i].Details,
              prevRecalculatedHash))

          if records[i].CurrentHash != expectedHash {
              invalidBlocks++
              invalidBlockNumbers = append(invalidBlockNumbers,
                  records[i].BlockNumber)
          }

          prevRecalculatedHash = expectedHash
      }

      return map[string]interface{}{
          "total_blocks":          len(records),
          "invalid_blocks":        invalidBlocks,
          "invalid_block_numbers": invalidBlockNumbers,
          "is_valid":              invalidBlocks == 0,
      }
  }

  9.4. Client-side File Verification

  Pengguna dapat mengupload file untuk memverifikasi keasliannya:

  Step 1: User memilih file (PDF, JPG, PNG, TXT) via dialog upload
  Step 2: Browser menghitung SHA-256 hash via Web Crypto API
          (crypto.subtle.digest) -- hash dihitung di CLIENT
  Step 3: Hash dikirim ke server untuk dicocokkan dengan ledger
          blockchain via GET /blockchain/block/search
  Step 4: Hasil verifikasi:
          - "Dokumen 100% Asli" jika hash ditemukan di ledger
          - "Hash Tidak Terdaftar" jika tidak ditemukan

  Keamanan: File fisik TIDAK pernah diupload ke server, hanya
  hash-nya yang dikirim. Privasi data tetap terjaga.

  Implementasi JavaScript:

  function showFileVerify() {
      Swal.fire({
          title: 'Verifikasi Berkas',
          input: 'file',
          inputAttributes: {
              'accept': '.pdf,.jpg,.jpeg,.png,.txt'
          },
          confirmButtonText: 'HITUNG HASH',
          showCancelButton: true
      }).then(function(file) {
          if (!file.value) return;

          var reader = new FileReader();
          reader.onload = function(e) {
              crypto.subtle.digest('SHA-256', e.target.result)
              .then(function(hashBuf) {
                  var hashArr = Array.from(new Uint8Array(hashBuf));
                  var hashHex = hashArr.map(function(b) {
                      return b.toString(16).padStart(2, '0');
                  }).join('');

                  fetch('/blockchain/block/search?hash='
                      + encodeURIComponent(hashHex))
                  .then(function(r) { return r.json(); })
                  .then(function(data) {
                      if (data.found) {
                          // Dokumen ASLI
                      } else {
                          // Hash tidak terdaftar
                      }
                  });
              });
          };
          reader.readAsArrayBuffer(file.value);
      });
  }

================================================================================
  11. KEAMANAN DAN LIMITASI
================================================================================

  11.1. Kekuatan

  (a) Deteksi manipulasi: Setiap perubahan data terdeteksi melalui
      verifikasi hash chaining

  (b) Anti-tamper via perhitungan ulang: Verifikasi menggunakan
      prevRecalculatedHash (bukan previous_hash tersimpan), sehingga
      manipulasi database tetap terdeteksi

  (c) Audit trail lengkap: Semua perubahan tercatat dengan user,
      waktu, IP address, dan user agent

  (d) Client-side file verification: File diverifikasi tanpa harus
      diupload ke server (privasi terjaga)

  11.2. Keterbatasan

  (a) Single point of trust: Keamanan bergantung pada keamanan
      database server karena private blockchain dengan satu authority

  (b) Tidak terdesentralisasi: Tidak ada distribusi data ke banyak
      node, sehingga jika database hancur, data blockchain hilang

  (c) Backup dependency: Keandalan blockchain bergantung pada backup
      database rutin

  (d) Immutable: Data yang sudah dicatat tidak bisa dihapus atau
      diubah, yang bisa menjadi masalah kepatuhan GDPR (right to
      erasure)

  11.3. Mitigasi

  (a) Regular backup database dengan enkripsi
  (b) Logging tambahan di level sistem operasi
  (c) Access control ketat ke database (hanya aplikasi yang bisa
      menulis)
  (d) Untuk kepatuhan GDPR: data sensitif tidak disimpan di field
      details, hanya referensi ID

  13. KESIMPULAN
================================================================================

  Blockchain SIMARC adalah cryptographic audit trail yang dirancang
  khusus untuk sistem kearsipan dengan tujuan:

  1. Menjamin integritas data arsip melalui SHA-256 hash chaining
  2. Mendeteksi setiap bentuk manipulasi data, termasuk modifikasi
     langsung di database
  3. Memberikan transparansi penuh melalui Blockchain Explorer
  4. Memungkinkan verifikasi keaslian dokumen fisik melalui hash
     matching tanpa mengupload file ke server
  5. Memenuhi kebutuhan kepatuhan dan regulasi kearsipan

  Sistem ini bukan cryptocurrency atau smart contract platform --
  melainkan tools anti-tamper untuk memastikan data arsip tetap
  asli, utuh, dan dapat diaudit kapan saja.
